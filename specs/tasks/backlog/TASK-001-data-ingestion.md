# TASK-001: Data Ingestion Module (V1)

- **Status**: backlog

## Objective

Implement a minimal, end-to-end ingestion pipeline: given a single Markdown (`.md`) source file, preserve the source, extract atomic knowledge assertions from it through a pluggable LLM provider, and write those assertions to disk as review-pending Proposal items. This is the first concrete implementation of the canonical conceptual flow defined in `specs/domain/knowledge-model.md`: `SOURCE → AI INTERPRETATION/EXTRACTION → PROPOSAL`. The pipeline stops at PROPOSAL — human review (accepting/rejecting a proposal into canonical knowledge) is explicitly a separate, future ticket.

This ticket is deliberately self-contained and independent of any prior ticket or existing code in this repository (including `knowledge_core/storage.py`). It implements its own minimal file-writing logic rather than depending on or importing any other module, per explicit product decision. It must still conform to the already-`Accepted` architecture decisions listed under Context, because those are binding regardless of which code implements them.

## Context

- `specs/domain/knowledge-model.md`: defines the conceptual flow `INPUT → SOURCE → AI INTERPRETATION/EXTRACTION → PROPOSAL → HUMAN REVIEW → CANONICAL KNOWLEDGE`, and defines Source ("original material... may need interpretation or extraction to become knowledge"), Assertion ("a statement or proposition that claims something to be true or valid... typically generated by AI processing of sources... may represent facts, interpretations, relationships, or inferences"), and Proposal ("a knowledge item that has been generated by the system but has not yet been accepted into canonical status").
- `specs/decisions/ADI-001-canonical-persistence-model.md` (Accepted): canonical knowledge is stored as one structured file per item (YAML frontmatter + body), under domain-scoped directories, with stable explicit IDs. No database, no git. Atomic writes required for any process writing into the shared vault tree.
- `specs/decisions/ADI-004-obsidian-role.md` (Accepted): the vault root is organized `<domain>/<item-type-plural>/<item-id>/<item-id>.md`. The five item-type folders it names are `entities/assertions/events/relationships/proposals`. **This ticket adds a sixth folder, `sources/`, per domain**, to hold preserved raw source material — required by CAP-002 ("Store source materials separately from extracted knowledge") and UC-001 ("Source acquisition and preservation" as processing stage 1), neither of which ADI-004 accounted for when it was written. This is treated as a minor, consistent extension of ADI-004's folder convention, not a contradiction of it — flagged here explicitly rather than decided silently.
- `specs/decisions/ADI-005-sync-vs-async.md` (Accepted), Rule 1: "Anything requiring AI/LLM processing... is asynchronous. Ingestion/extraction (UC-001, UC-007)... run as background tasks. Their result is a Proposal added to the review queue... the user is never blocked waiting on them." In-flight task state must be persisted locally, outside the vault, per-device, recoverable — not added as an afterthought.
- `specs/decisions/ADI-007-implementation-language.md` (Accepted): implemented in Python.
- `specs/decisions/ADI-008-llm-provider-architecture.md` (Accepted): the extraction step must call the runtime LLM only through a pluggable provider interface (e.g. `extract(text, context) -> ExtractionResult`). Ingestion logic must never import or reference a specific provider SDK directly. The active provider is chosen by local config, never hardcoded. This ADR does not mandate a specific default provider — this ticket is free to pick the simplest one to wire (a local Ollama endpoint is explicitly suggested in the ADR as the simplest starting point).
- `specs/domain/knowledge-invariants.md`:
  - INV-001 (Universal Human Validation): ingestion must never write anything directly to canonical status — its only output is Proposal items.
  - INV-002 / INV-016 (AI Inference Is Not Sourced Fact / Source Content and Interpretation Remain Distinguishable): extracted assertions must be marked with an `epistemic_status` that distinguishes them from directly-sourced fact, and must carry provenance back to the exact source they came from.
  - INV-003 (Provenance): every Proposal must be traceable to its source material and the processing step that produced it.
  - INV-007 (Temporal Validity): the system must distinguish when a source was ingested/recorded from when its content claims to be true/applicable.
  - INV-019 (Failures Must Degrade Safely): a failed extraction must not corrupt the source or leave a partially-written Proposal file; it must leave inspectable, honest failure state instead.
  - INV-020 (Repeated Ingestion Must Be Safe): re-ingesting the same source content must not blindly create duplicate proposals.
- `specs/product/capabilities.md`, CAP-002 (Human-Reviewed Knowledge Ingestion): "Store source materials separately from extracted knowledge"; "All canonical knowledge must be human-reviewed and accepted"; "AI-generated information cannot automatically become canonical."
- `specs/product/use-cases.md`, UC-001 (Novel Ingestion) and UC-007 (Multimodal Ingestion) are the framing use cases; UC-016 (Duplicate/Repeated Ingestion) frames the duplicate-safety requirement. Both UC-001 and UC-007 cite a capability "A définir — Source and Ingestion Management" — there is no formal `CAP-CORE-XXX` entry for ingestion yet in `specs/architecture/capabilities.md`. This is an already-documented gap in the spec corpus, not an omission introduced by this ticket; this ticket fills it at the implementation level without requiring a new ADR, since the structural decisions it depends on (file storage, async execution, pluggable provider) are already `Accepted`.

## Scope

Implement a Python package providing an ingestion pipeline that:

1. Reads a single Markdown source file from a given path.
2. Preserves that source as a canonical-compatible file under the vault.
3. Detects exact-duplicate re-ingestion (by content hash) and skips re-processing if the source was already ingested.
4. Calls a pluggable LLM provider to extract a list of atomic assertions from the source text.
5. Writes each extracted assertion as a Proposal file under the vault, with `proposal_status: PROPOSED`.
6. Tracks the state of each ingestion attempt (pending/running/completed/failed) in local, non-canonical storage outside the vault.

### V1 scope decisions (explicit assumptions — flag disagreement rather than silently deviate)

- **Only the Assertion item type is extracted.** Entity, Event, and Relationship extraction (UC-001 processing stages 3–6: candidate entity identification, event identification, relationship mapping, temporal extraction) are each a separate extraction problem and are out of scope for this ticket.
- **Only `.md` source files are supported in V1**, but source reading is behind an extensible interface (a reader registry keyed by file extension) so that adding a new format later (PDF, audio, etc., per UC-007) means adding a new reader, not modifying the pipeline.
- **`domain` is passed explicitly as a parameter to the pipeline**, never inferred, per INV-008/AP-005 and UC-001's precondition that the system is already configured with the applicable domain.
- **Only one concrete LLM provider is required for V1** (a local Ollama HTTP endpoint is recommended, consistent with this project's local-first posture and ADI-008's own suggestion), reached only through the `extract()` interface — never called directly from pipeline code.
- **Duplicate detection is exact-content-hash only.** Detecting a *modified* re-ingestion of a previously-seen source (UC-003, the richer scenarios in UC-016) is explicitly out of scope.
- **Task state tracking is minimal**: one local record per ingestion attempt with a status field and enough information to know what happened — not a general-purpose task queue or orchestrator.

### File layout (exact contract)

```
<vault_root>/<domain>/sources/<source_id>/<source_id>.md
<vault_root>/<domain>/proposals/<proposal_id>/<proposal_id>.md
```

- `domain` ∈ {PERSONAL, FICTION, LEARNING, RESEARCH, PUBLISHING} (per AP-005/INV-008), passed explicitly by the caller.
- `source_id` is derived deterministically from the source content, e.g. `src-<sha256(content)[:16]>`. This makes exact-duplicate detection equivalent to "does a source file with this ID already exist" — no separate duplicate index is needed.
- `proposal_id` is a fresh unique identifier per assertion, e.g. `prop-<uuid4>`.
- No history subfolder is required by this ticket: sources and proposals are only ever created, never updated, within this scope (duplicate ingestion is skipped rather than triggering an update path). If this function is ever called again for an existing `source_id`, the correct behavior is "detect duplicate, skip" (see Acceptance Criterion 4) — not an update/overwrite.
- Each `.md` file is standard YAML frontmatter (`---`-delimited) followed by a markdown body.

### Required frontmatter fields — Source file

- `id` (string, matches `source_id`)
- `type`: `source`
- `domain` (string, one of the five domains)
- `source_format` (string, e.g. `markdown`)
- `original_filename` (string)
- `content_hash` (string, sha256 hex digest of the raw content)
- `ingested_at` (ISO 8601 timestamp)
- `lifecycle_status`: `ACTIVE`

The body of the source file is the original file content, byte-for-byte preserved (or a faithful text reproduction if binary preservation is impractical for `.md` — trivial for this ticket since `.md` is already plain text).

### Required frontmatter fields — Proposal file

- `id` (string, matches `proposal_id`)
- `type`: `proposal`
- `domain` (string, same domain as the source)
- `proposal_status`: `PROPOSED` (this ticket only ever writes this value; the full lifecycle `PROPOSED → EDITED → ACCEPTED → CANONICAL` or `PROPOSED → REJECTED`, per `technical-requirements.md` KSR-007/KSR-013, is future work)
- `proposed_item_type`: `assertion` (what kind of canonical item this proposal would become if accepted — fixed to `assertion` in this ticket's scope)
- `epistemic_status` (string, one of `direct`/`inferred`/`uncertain`/`contested` — extraction output should default to `inferred` unless the provider signals otherwise)
- `created_at` (ISO 8601 timestamp — when this proposal was generated)
- `valid_from` / `valid_until` (ISO 8601 timestamp or null — claimed validity of the asserted content, distinct from `created_at`, per INV-007)
- `provenance` (dict): must include at minimum `source_id` (pointer to the Source file above) and `extraction_provider` (name/identifier of the provider that produced it)

The body of the proposal file is the extracted assertion's text itself — the full content of what would become the canonical Assertion item if this proposal is later accepted (a full embedded snapshot, not a reference-only diff, consistent with ADI-001's "full snapshots, never diffs" philosophy applied to proposal content).

### Provider interface (per ADI-008)

```python
@dataclass
class ExtractedAssertion:
    text: str
    epistemic_status: str  # "direct" | "inferred" | "uncertain" | "contested"

@dataclass
class ExtractionResult:
    assertions: list[ExtractedAssertion]

class Provider(Protocol):
    def extract(self, text: str, context: dict) -> ExtractionResult: ...
```

Pipeline code may only depend on this interface. Exactly one concrete implementation is required for V1 (e.g. `OllamaProvider`), living in its own module, the only place allowed to perform the actual HTTP/SDK call to the LLM. Provider selection (which concrete class to instantiate) happens via local configuration (a config file or environment variable), never a hardcoded import inside the pipeline.

### Reader interface (source-format extensibility)

```python
class SourceReader(Protocol):
    def read(self, path: Path) -> str: ...  # returns raw text content
```

A registry maps file extension (or MIME type) to a `SourceReader` implementation. V1 requires exactly one registered reader, for `.md`. Adding a second file type in the future must only require registering a new reader, not modifying pipeline orchestration logic (see Acceptance Criterion 6).

### Task state

One record per ingestion attempt, persisted as a local file (JSON or equivalent) outside the vault (per ADI-005's placement rule — local, per-device, not synced, not canonical). Minimum fields: `task_id`, `source_path`, `domain`, `status` (`pending`/`running`/`completed`/`failed`/`skipped_duplicate`), `started_at`, `completed_at` (nullable), `error` (nullable), `source_id` (nullable until resolved), `proposal_ids` (list, empty until populated). Loss of this state must never corrupt or affect canonical/proposal data — per ADI-005, the safe fallback on lost task state is that the ingestion attempt must simply be resubmitted.

## Requirements

- Python only (ADI-007). `pyyaml` for frontmatter; an HTTP client (`requests` or the standard library) for the Ollama provider — no other new dependency without a stated reason.
- All directory creation (domain folder, `sources/`/`proposals/` folders, per-item folder) must happen automatically as needed.
- Missing or invalid required frontmatter fields must raise a clear, typed validation error before any file is written.
- No use of git anywhere in the implementation (per ADI-001).
- Must not depend on Obsidian being installed or running.
- All writes to `sources/` and `proposals/` files must be atomic (write to a temp file in the same directory, then `os.replace()` or equivalent).

## Constraints

- No Entity/Event/Relationship extraction — Assertion only.
- No proposal accept/reject/edit workflow — this ticket stops at writing `proposal_status: PROPOSED` files.
- No database of any kind (SQLite or otherwise) — task state and duplicate detection are plain files, not a database.
- No GUI or CLI required (a Python function entry point is sufficient).
- No semantic/fuzzy duplicate detection — exact content-hash match only.
- No dependency on `knowledge_core/` or any other existing module in this repository. This ticket implements its own minimal atomic file-writing logic, even though it produces files that follow the same frontmatter contract ADI-001/ADI-004 already mandate. (This creates known short-term duplication with `knowledge_core/storage.py`'s equivalent logic — accepted as a consequence of this ticket's explicit independence; a future ticket may consolidate them once both have proven their contracts in practice.)

## Acceptance criteria

1. Ingesting a `.md` source file produces a Source file at `<domain>/sources/<source_id>/<source_id>.md` with all required frontmatter fields, and one Proposal file per extracted assertion at `<domain>/proposals/<proposal_id>/<proposal_id>.md` with all required frontmatter fields, including `proposal_status: PROPOSED` and `provenance.source_id` pointing at the Source file just created.
2. No pipeline code (`ingestion/pipeline.py`, `ingestion/storage.py`, `ingestion/readers/*`) imports or references a concrete LLM SDK/HTTP client directly — only `ingestion/providers/ollama_provider.py` (or an equivalent single provider module) does. Verifiable by static inspection.
3. Ingesting the exact same source file a second time (same content, same domain) does not create a new Source file or any new Proposal files — the pipeline detects the existing `source_id` and returns a result indicating a skipped duplicate, per INV-020.
4. If the provider's `extract()` call raises/fails (simulated in a test), no partial or corrupt Source or Proposal file is left on disk, the original input file is untouched, and the task state record reflects `status: failed` with a non-null `error`.
5. Adding a second registered reader (e.g. a trivial `.txt` reader used only in a test) requires no changes to `ingestion/pipeline.py` — only a new reader module plus a registry entry.
6. Swapping the configured provider for a second, minimal test/fake provider (implementing the same `Provider` protocol) requires no changes to `ingestion/pipeline.py` — only local configuration.
7. Every extracted assertion's Proposal frontmatter includes an `epistemic_status` value from `{direct, inferred, uncertain, contested}` — never omitted, never silently defaulted to something implying certainty.
8. All Source/Proposal writes are atomic: verified either by inspecting for temp-file-then-rename behavior in code, or by simulating a failure mid-write and confirming no partial file is left behind.
9. `grep -r "git"` over the `ingestion/` implementation shows no use of git tooling/libraries for historization.

## Testing requirements

`pytest` unit tests covering every acceptance criterion above. Use `tmp_path` (or equivalent) as `vault_root` and a local temp directory for task state — tests must never touch a real Obsidian vault or write anything outside their own temp directories. The LLM provider must be mocked/faked in tests (no real network calls to Ollama or any other service in the test suite) except, optionally, one clearly-marked integration test that is skipped by default. Include at least:
- A first-ingestion test asserting the full file layout and frontmatter contract (Criterion 1).
- A static-inspection or import-graph test for provider isolation (Criterion 2).
- A duplicate-ingestion test (Criterion 3).
- A simulated provider-failure test (Criterion 4).
- A second-reader extensibility test (Criterion 5).
- A second-provider extensibility test (Criterion 6).

## Out of scope

- Entity, Event, and Relationship extraction — future ticket(s).
- Proposal review/accept/reject/edit workflow (AP-002) — future ticket, produces canonical knowledge from these proposals.
- Any file format other than `.md` (PDF, audio, video, images, web pages — UC-007) — future ticket(s), enabled by the reader registry this ticket establishes.
- Semantic/near-duplicate detection, staleness detection on source modification (UC-003, richer parts of UC-016).
- A real asynchronous task orchestrator/queue — this ticket only defines the task-state record shape, not a scheduler.
- Any GUI or CLI.
- A second or third concrete LLM provider beyond the one required for V1.
- Consolidating this module's storage logic with `knowledge_core/storage.py` or any other existing module.
